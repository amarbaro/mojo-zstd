## What it does

<!-- Stable description of the program. Carried forward from the previous note; edit only when the product itself changes.
     3 to 6 lines: what it is, who uses it, where it runs (URL/port/binary), how to start it. -->
zstd and lz4 frame compression for Mojo, in pure Mojo: one-shot `compress`/`decompress`, and
streaming zstd files or buffers through a 128 KiB window. No C library, no foreign calls, no linker flag.

## Highlights

<!-- 1 to 5 bullets a user would notice. Lead with the benefit, not the implementation. -->
- No system library any more: both codecs are native Mojo ports of the reference algorithms, so `libzstd-dev` and `liblz4-dev` are no longer needed.
- Same answers as the C libraries: decoding accepts and rejects exactly what libzstd and liblz4 do, lz4 output is byte for byte python-lz4's, zstd output decodes under Python and stays within 5% of libzstd's size at every level.
- Speed near the C libraries on 32 MiB text at level 3: zstd compress 84 to 95 ms (libzstd via Python 56 to 87), lz4 compress 28 to 37 ms (38 to 46).

## Changes

### Added
- Native zstd decoder (frames, FSE, Huffman, sequences, xxh64) and encoder (fast to btultra2 strategies, block pre-splitting).
- Native lz4 frame and block decoder and encoder, xxh32.

### Changed
- `ZstdWriter` is native; `src/` has no C calls left. The public API is unchanged.

### Fixed
- The hash3 table is rebased with the others; inputs whose indices cross 2^31 are tested.

## Known limits

<!-- Honest list: slow paths, unsupported cases, flaky upstreams, anything UNVERIFIED. -->
- `compress` inputs under 2 GiB. No dictionaries, multithreading, long-distance matching, lz4 block format or lz4 levels.
- zstd decompress is slower than libzstd (48 to 73 ms against 35 to 50 on 32 MiB).
- `pkg-conda` was not re-run for this version.
